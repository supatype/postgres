# Durable-write scale-out — sustained drain rate vs persistence workers
# burst=300000 distinct keys (-r 5000000), 512B, ring_mb=256 each, 4-vCPU
workers   |   drain rate/s |  dropped | table rows
1         |          57672 |        0 |     276920
2         |         103001 |        0 |     291175
4         |         145083 |        0 |     291096

# Interpretation
# - Durable write throughput scales with persistence workers: 1.0x / 1.8x / 2.5x
#   at 1 / 2 / 4 workers (57k -> 103k -> 145k/s), zero drops.
# - Sub-linear at 4 because: (a) 4 vCPU shared by 1 RESP + N persist workers +
#   the load client; (b) all workers commit to ONE Postgres WAL, so fsync/WAL
#   insertion serializes — the shared-WAL ceiling. This is the durable-path
#   analogue of "Valkey wins by not sharing" (§11): persistence ultimately
#   serializes on WAL, which is why the product bet is per-prefix durability +
#   SQL access, not out-raw-writing Valkey.
# - Keys are sharded by CRC16 slot across rings, so a given key always lands on
#   the same worker: no cross-worker ON CONFLICT contention.
