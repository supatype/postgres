# P1 — storage & durability, measured in-PG (relaxed tier)
# tier=relaxed (batched SPI upsert into supacache.kv), persist_window=10ms,
# 8 hash partitions, single worker, 512B values, 4-vCPU box.

## Backing tables (§3.3)
- supacache.kv hash-partitioned over 8 partitions (tenant, key).
- RESP writes land in the table; SELECT over supacache.kv and supacache.get()
  return the same bytes ("SQL access to the same bytes", §14).
- Even hash distribution across partitions (118-134 per partition at n=1000).

## RESP SET throughput — persisted vs ephemeral (single worker)
                     ephemeral    relaxed(persisted)   ratio
  pipelined -c50 -P16   556k/s          32.4k/s        ~17x slower
  closed-loop p50        39us            39us          equal (async ack)
  closed-loop avg        33us            69us          +36us (flush jitter)

## Crash recovery (§12 P1)
- Hard kill -9 of the whole cluster, then restart:
    5,000 keys   recovered in   6.9 ms   (~1.4 us/key)
  104,290 keys   recovered in 366.9 ms   (~3.5 us/key)
- Every key survived the crash and is served over RESP after restart;
  PG WAL crash-recovery replays the committed supacache.kv rows first.

## Findings
- Reads are unaffected by persistence: still ~500k/s, 34us (P0 numbers hold).
- Persisted WRITE throughput is bounded by (a) per-row SPI ON CONFLICT upserts
  and (b) the flush transaction blocking the single event-loop thread (visible
  as per-second jitter 18k-52k). The production path should offload persistence
  (multi-row INSERT / COPY, or a dedicated I/O worker, or the XACT_EVENT_COMMIT
  publication of §3.5) rather than upserting row-by-row on the event loop.
- relaxed's async ack keeps write latency at ephemeral levels (p50 39us) while
  the data reaches durable tables within one window — the plan's default tier
  (§3.4) behaves as specified.
