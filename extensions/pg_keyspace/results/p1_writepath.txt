# P1 write-path optimization — measured in-PG (relaxed tier, 512B, 4-vCPU)
# Goal: remove the persisted-write bottleneck found in the first P1 cut
# (row-by-row SPI upserts on the event-loop thread: 32k/s, and reads stalling
# behind flushes with a 170ms tail).

## Step 1 — bulk UNNEST upsert (still inline on the event loop)
- Replaced per-row INSERT..ON CONFLICT with ONE deduped multi-row upsert via
  unnest($1::bytea[], $2::int[], $3::bytea[], $4::bigint[]) per window.
- Persisted pipelined SET: 32.4k/s -> 85.3k/s  (~2.6x).
- But reads still stalled behind the flush (event loop blocked ~9ms/window).

## Step 2 — decouple: SPSC shmem ring + dedicated persistence worker
- RESP worker now only enqueues into a lock-free shared-memory ring (~ns);
  a separate persistence background worker (its own process + SPI connection)
  drains the ring and bulk-upserts. The RESP event loop never touches SPI.

### Read latency under heavy concurrent write load (GET -c1 -P1, SET -c50 -P16)
                          baseline    inline flush (step1)   ring+worker (step2)
  GET avg                  33 us          241 us                 82 us
  GET p99                  55 us          1.80 ms                1.75 ms
  GET max                 375 us        170.8 ms                 4.95 ms   <-- 34x
- The catastrophic 170ms tail is gone: reads are no longer blocked by
  persistence. Residual p99 ~1.75ms is event-loop CPU contention from the
  50-connection pipelined write flood, not persistence (a second slot worker,
  §3.1 P4, would remove it).

### Sustained persistence (one persistence worker)
- Clean burst that fits the ring (100k writes): 0 dropped, fully persisted in
  0.93s => ~107k writes/s drained and committed to supacache.kv.
- Under sustained overload beyond the drain rate, the ring absorbs the burst
  then sheds (ring_stats.dropped rises) — best-effort relaxed semantics. Knobs:
  bigger pg_keyspace.ring_mb (longer bursts), more persistence workers /
  partitioned rings (higher ceiling), or producer backpressure (no loss, at the
  cost of slowing writers).

### Crash recovery still intact with the two-worker design
- 8,000 keys recovered from supacache.kv in 8.0ms after a SIGQUIT crash;
  104k keys in ~370ms earlier (~3.5us/key). Every key survived.

## Net
- Reads: unaffected by writes (tail 170ms -> 5ms).
- Durable writes: off the event loop, ~107k/s sustained per persistence worker
  (up from 32k/s), decoupled and crash-safe.
- Remaining ceiling is the SPI upsert rate per worker; raise it with more
  persistence workers or COPY-into-staging + merge (future).
