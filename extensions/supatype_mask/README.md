# supatype_mask

Per-column read masking and write rejection, driven by security labels and enforced in
the planner.

```sql
SECURITY LABEL FOR supatype ON COLUMN public.posts.salary
  IS 'MASK READ public.can_read_posts__salary WRITE public.can_write_posts__salary';
```

From then on, every reference to `posts.salary` — in the target list, in a `WHERE`
clause, through a view, inside a subquery, in `COPY posts TO` — is rewritten to

```sql
CASE WHEN public.can_read_posts__salary(posts) THEN posts.salary ELSE NULL END
```

and every assignment to it is rewritten to preserve, accept or reject per row.

**Reads mask, writes reject.** A rejected write is an error the caller should see; an
unauthorised read is a null.

## Why a planner hook and not privileges or views

`GET /posts` with no `select` parameter sends `SELECT posts.*`. That names every column,
so it succeeds only if the role holds `SELECT` on every column — a column `REVOKE` makes
PostgREST answer **403 for the whole table** rather than returning a filtered row. So a
read restriction cannot be a privilege: the column has to be present and masked.

Masking is a per-row expression, and the only things in Postgres that put an expression
where a column was are a view and a query rewrite. `CREATE VIEW v AS SELECT * FROM t`
does not store `*` — Postgres expands it at creation and stores a fixed target list, so a
column added later is invisible to the API until something re-runs `CREATE OR REPLACE
VIEW`. Every view is a snapshot of the column list.

That leaves the rewrite, which also reaches psql, logical-decoding catch-up queries and
anything else talking to the database rather than only what PostgREST is pointed at.

## The rules live in SQL, not in C

The extension does not implement a rule language. It calls the predicate the label names.
Those functions are generated by the Supatype schema engine from the same access AST that
produces the RLS policies, so a UI, a policy and a mask are one expression rather than
three that drift. This is what keeps a security-critical C extension small.

A predicate takes the table's composite type and returns boolean:

```sql
CREATE FUNCTION can_read_posts__salary(posts posts) RETURNS boolean
  LANGUAGE sql STABLE AS $$
    SELECT author_id = auth.uid() FROM (SELECT ($1).*) AS posts;
  $$;
```

## Install

Bundled in the `supatype/postgres` image. Two halves, and both are needed:

```conf
# postgresql.conf -- registers the label provider and the hooks
shared_preload_libraries = '..., supatype_mask'
```

```sql
-- supplies the rejection function
CREATE EXTENSION supatype_mask;
```

Preloading without the extension still masks; a rejection then raises
`supatype_mask.deny() is not available` instead of the intended error. The reverse — the
extension without the preload — does nothing at all. Dropping the extension therefore does
**not** unmask anything, which is the right way round.

`shared_preload_libraries`, not `session_preload_libraries` — see below.

## Configuration

| GUC | Default | Context | Notes |
|---|---|---|---|
| `supatype_mask.exempt_roles` | `service_role` | `PGC_SIGHUP` | Comma-separated. Read masked columns unmasked. |
| `supatype_mask.enabled` | `on` | `PGC_SIGHUP` | Break-glass. Logs at `LOG` level on every backend start while off. |

Exemption is an explicit role list plus superusers, matched against the current effective
role. Never "is the table owner": ownership is incidental to whether a caller should read
a masked column, and PostgREST connecting as the owner is precisely the case that would
make the whole mechanism a no-op.

## Tamper resistance

Both settings are `PGC_SIGHUP` and the library is in `shared_preload_libraries`, so
**there is no SQL statement that disables masking for a role, a database or a session** —
not even for a superuser. This is deliberate, and it is the same posture `pg_guard` takes
with all of its own settings.

The reasoning is an asymmetry: every *other* way to stop a column being masked leaves a
trace. Dropping a label or a predicate is a schema change the differ reports on the next
push, and the push re-asserts it. A GUC leaves nothing. So the GUC is the weakest link
and has to be the hardest to reach.

Two routes were open before and are now closed:

| Route | Why it mattered | Now |
|---|---|---|
| `ALTER ROLE authenticated SET supatype_mask.enabled = off` | Permanent, invisible, unmasks every column for the whole API surface in one statement | `PGC_SIGHUP` — refused |
| `ALTER ROLE authenticated SET session_preload_libraries = 'pg_guard'` | Narrows the preload for just the data-plane role, so the library never loads for it | Library is in `shared_preload_libraries` (`PGC_POSTMASTER`), which cannot be set per role or per database |

What remains is `ALTER SYSTEM SET shared_preload_libraries` plus a **server restart** —
superuser only, written to `postgresql.auto.conf` on disk, and it takes every other
preloaded extension down with it. Loud and global rather than silent and targeted, which
is the distinction that matters. A superuser is exempt from masking anyway, and can
equally `DISABLE ROW LEVEL SECURITY`; this is no weaker than RLS against the same actor.

## Behaviour

| Statement | Result |
|---|---|
| `SELECT`, any reference | masked to NULL per row |
| `WHERE`, `ORDER BY`, `GROUP BY`, joins, subqueries | masked, so a qual cannot be used as an oracle |
| `sum(salary)` etc. | rejected per unreadable row, so a total is either correct or an error — never quietly partial |
| `UPDATE`, caller may write | accepted |
| `UPDATE`, caller cannot read | old value preserved silently |
| `UPDATE`, caller can read but not write | rejected |
| `INSERT` | accepted for an identity-only write rule; coerced to the column default otherwise |
| `COPY t TO` | rewritten through the planner, so masked |
| `COPY t FROM` | refused |
| `MERGE` | refused |
| whole-row reference (`to_jsonb(t)`, `SELECT t FROM t`) | refused |

**The UPDATE round-trip is the case this exists for.** A client GETs a row, `salary`
comes back null because it is masked, the user edits the title, and the client PATCHes
the whole object back including `salary: null`. Without coercion the real salary is gone,
silently, with a 200. "Could not read it" and "saw it and changed it" have to be
distinguishable, or one of them destroys data and the other breaks whole-object clients.

**INSERT is the honest limitation.** There is no old row, so the write predicate is
evaluated against `NULL::t`. An identity-only rule (`Role<"admin">`) answers correctly; a
row-dependent one (`Owner<"author_id">`) compares against NULL, yields NULL, and the
column falls back to its default. Fail closed rather than accept an unauthorised value.

## Fail-closed states

Every undecidable case masks rather than exposes:

- a label naming a predicate that does not exist
- a predicate that does not return boolean
- a predicate declared `IMMUTABLE` — see below
- an unparseable label

Each logs a `WARNING` naming the column. A malformed label is normally rejected at
`SECURITY LABEL` time by the provider's validation callback, so these states mean the
label was written while the library was not loaded.

**Why `IMMUTABLE` is refused.** A masking predicate reads the caller's claims, so it is
`STABLE` at best. Declared immutable, the planner is entitled to fold it wherever its
arguments are constant — which the INSERT path does deliberately — and a folded answer
baked into a cached plan is a cross-caller leak. Five lines of catalog check; the whole
design rests on them.

## What this does not cover

- **Logical replication.** WAL records are not query results, so nothing here filters
  them. Realtime evaluates the same `can_read_*` functions against the WAL record cast to
  the table's composite type, in the subscriber's transaction.
- **Inference through error messages.** A non-leakproof operator applied to the *predicate's*
  own inputs can still disclose something through an error. References to the masked
  column itself are safe: the substitution happens at the `Var`, so the real value never
  reaches any operator.
- **Exempt roles.** `service_role` and superusers see everything, by design.
- **Postgres before 17.** The rewrite touches `Var`, `Query` and the node walkers, which
  are not stable across majors.

## Tests

```bash
docker build -t supatype-mask-build -f test/Dockerfile test
docker run --rm -v "$PWD:/src" -w /src supatype-mask-build bash -c \
  "make install && chown -R postgres /tmp && su postgres -c 'SKIP_INSTALL=1 bash test/run-tests.sh supatype_mask'"
```

The server cannot run as root, hence the two-step: install as root, test as `postgres`.

The suite asserts the things the design was gated on, including a prepared statement
executed under `force_generic_plan` as two different identities giving two different
answers. That one is non-negotiable: a plan built for an admin and reused for a
non-admin would leak the column with no error and no log line.
